# Сервис оформления и проверки документов по ГОСТ и своим требованиям — дизайн

Дата: 2026-10-15
Статус: согласован в чате, ждёт проверки спецификации

## 1. Цель

Веб-сервис для студентов и авторов учебных и технических работ: загрузить
документ (DOCX или обычный текст), выбрать набор требований — готовый ГОСТ
или свой профиль — и получить либо отчёт с замечаниями, либо оформленный DOCX.

Отличие от аналогов (например, gostdoc.ru): пользователь сам задаёт требования
в форме — берёт ГОСТ за основу, меняет отдельные параметры и сохраняет как
свой профиль («Моя методичка»).

**Критерии успеха первой версии**

- Документ по ГОСТ 7.32-2017 с типичными ошибками (шрифт, поля, интервалы,
  отступы, заголовки, подписи) после режима «Оформить» проходит повторную
  проверку без ошибок по автоисправимым правилам.
- Текст документа (слова) не меняется — проверяется автотестом.
- Свой профиль создаётся из ГОСТ-профиля, редактируется в форме, сохраняется
  в аккаунте и применяется так же, как ГОСТ.

## 3. Пользовательский сценарий

1. **Вход** — регистрация по email и паролю.
2. **Загрузка** — DOCX (до 20 МБ) или вставка обычного текста. Текст
   разбирается на структуру: заголовки («1 Введение», «1.1 …», «ВВЕДЕНИЕ»),
   списки, подписи «Рисунок N», «Таблица N», источники.
3. **Выбор профиля** — готовый ГОСТ или свой.
4. **Режим**:
   - *Проверить* — тот же DOCX с комментариями Word: пункт требований,
     ожидаемое и найденное значение;
   - *Оформить* — исправить всё автоисправимое, остальное — комментариями.
5. **Результат** — экран с замечаниями по важности, PDF-предпросмотр,
   скачивание DOCX.
6. **История** — список прошлых документов; файлы удаляются через 30 дней.

Сервис не исправляет сам, а только комментирует: отсутствие обязательных
разделов, их порядок, ссылки на несуществующие рисунки и таблицы, неполные
библиографические записи.

## 4. Профиль требований

Профиль — JSON-документ с метаданными и группами правил:

```json
{
  "id": "gost-7.32-2017",
  "name": "ГОСТ 7.32-2017 — Отчёт о НИР",
  "base": null,
  "readonly": true,
  "rules": {
    "page.margins": {
      "value": {"top": 20, "bottom": 20, "left": 30, "right": 15},
      "severity": "error",
      "enabled": true,
      "source": "ГОСТ 7.32-2017, п. 6.1.1"
    }
  }
}
```

У каждого правила: `value`, `severity` (`error` | `recommendation`),
`enabled`, `source`. Свой профиль хранит `base` — id исходного ГОСТ-профиля.

**Группы правил (и разделы формы):**

1. Страница — формат, ориентация, поля.
2. Основной текст — шрифт, кегль, цвет, межстрочный интервал, абзацный отступ,
   выравнивание, интервалы до/после, переносы.
3. Заголовки, уровни 1–3 — регистр, жирность, выравнивание, отступ, точка в
   конце, формат номера («1», «1.1»), с новой страницы, интервалы.
4. Структурные элементы — обязательные разделы и их порядок, ненумеруемые
   разделы и оформление их заголовков.
5. Нумерация страниц — положение, с какой страницы показывать, шрифт.
6. Рисунки и таблицы — шаблон подписи, положение, выравнивание, сквозная или
   по разделам нумерация, вид тире, кегль в таблицах.
7. Формулы — выравнивание, формат номера «(1)» / «(1.1)», положение номера.
8. Списки — маркеры, формат нумерации.
9. Список источников — стандарт (Р 7.0.100-2018 / 7.1-2003), порядок
   (алфавит / по упоминанию), формат ссылок в тексте.
10. Типографика — «ёлочки», длинное тире, двойные пробелы, неразрывные пробелы.

**Логика формы**

- ГОСТ-профили только для чтения; «Создать свой на основе» делает копию.
- Поле, отличающееся от исходного ГОСТа, подсвечено; есть «сбросить к ГОСТу».
- Правило можно выключить — тогда оно не проверяется и не исправляется.
- Экспорт и импорт профиля в JSON.
- Профиль валидируется по схеме (Pydantic) при сохранении и импорте.

## 5. Движок

Конвейер из независимых модулей в `backend/engine/`:

1. **import** — DOCX открывается через python-docx (с доступом к XML через
   lxml). Обычный текст разбирается парсером структуры и собирается в DOCX
   с базовыми стилями. Дальше оба пути одинаковы.
2. **analyze** — строит модель документа: каждому абзацу назначается роль
   (основной текст, заголовок уровня N, подпись рисунка/таблицы, формула,
   элемент списка, источник, содержание, титульный лист). Роль определяется
   по стилю Word, а если стиля нет — эвристиками (шаблоны номеров, ключевые
   слова, жирность, кегль). Это ключевой по качеству модуль.
3. **rules** — каждое правило — класс:
   ```python
   class Rule:
       key: str                        # "page.margins"
       def check(self, doc, cfg) -> list[Issue]: ...
       def fix(self, doc, cfg) -> None: ...   # только у автоисправимых
   ```
   `Issue`: место в документе (индекс абзаца или раздела), ключ правила,
   `source`, `expected`, `actual`, `severity`, `fixable`.
4. **Режимы**:
   - «Проверить»: все `check` → комментарии Word с автором «ГОСТ-сервис»;
   - «Оформить»: все `fix` → повторный `check` → остаток в комментарии.
5. **render** — DOCX, JSON-отчёт, PDF через LibreOffice headless. LibreOffice
   также обновляет поле содержания и нумерацию страниц.

**Сохранность текста.** Движок меняет только оформление. Разрешённые
изменения текста — только типографика (кавычки, тире, пробелы). Инвариант:
текст до и после, нормализованный по этим символам, совпадает.

**Ошибки**

- Повреждённый, зашифрованный, не-DOCX или файл больше 20 МБ — отказ с
  понятным сообщением до постановки в очередь.
- Исключение в одном правиле логируется, правило пропускается, обработка
  документа продолжается; в отчёте — пометка «правило не выполнено».
- Ограничение на задачу — 2 минуты; по таймауту — статус «ошибка» и сообщение.

## 6. Архитектура и стек

- **Бэкенд**: Python 3.12, FastAPI, SQLAlchemy + Alembic, PostgreSQL.
- **Очередь**: Redis + RQ; фронтенд опрашивает статус задачи.
- **DOCX**: python-docx + lxml; **PDF**: LibreOffice headless в контейнере воркера.
- **Фронтенд**: Next.js (TypeScript) + Tailwind. Экраны: вход, загрузка,
  форма профиля, результат с PDF-предпросмотром, кабинет (профили, история).
- **Авторизация**: email + пароль, argon2, сессия в httpOnly-cookie.
- **Файлы**: локальный том, затем S3-совместимое хранилище; удаление через
  30 дней (периодическая задача).

**Модель данных**

- `users` — id, email, password_hash, created_at.
- `profiles` — id, user_id (NULL для ГОСТ-профилей), name, base_id, data (JSONB),
  created_at, updated_at. ГОСТ-профили загружаются из `backend/profiles/*.json`.
- `jobs` — id, user_id, profile_id, profile_snapshot (JSONB), mode, status,
  input_path, output_docx, output_pdf, report (JSONB), error, created_at,
  expires_at.

**API (основное)**

- `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`
- `GET /profiles`, `GET /profiles/{id}`, `POST /profiles` (в т.ч. из base),
  `PUT /profiles/{id}`, `DELETE /profiles/{id}`, `GET /profiles/{id}/export`,
  `POST /profiles/import`
- `POST /jobs` (файл или текст + profile_id + mode), `GET /jobs`,
  `GET /jobs/{id}`, `GET /jobs/{id}/docx`, `GET /jobs/{id}/pdf`

**Структура репозитория**

```
backend/
  api/        # FastAPI-роуты, схемы
  engine/     # import, analyze, rules/, render
  profiles/   # gost_7_32_2017.json, gost_2_105_2019.json, espd_19.json, gost_r_7_0_100_2018.json
  tests/      # фикстуры DOCX и тесты
frontend/
docker-compose.yml
docs/
DEPLOY.md
```

## 7. Деплой

GitHub Pages не подходит: нужны Python-сервер, база и LibreOffice.
`docker-compose` (api, worker, postgres, redis, frontend, nginx) на одном VPS
(Timeweb, Selectel или Yandex Cloud). Инструкция — в `DEPLOY.md`.
Аренда сервера, домен и секреты — на стороне владельца.

## 8. Тестирование

- Эталонные DOCX-фикстуры по каждому ГОСТу: правильные и с ошибками.
  Генерируются кодом, чтобы их было видно в диффе.
- Для каждого правила: тест `check` (находит ошибку) и `fix` (после него
  `check` пуст).
- Инвариант сохранности текста — на каждой фикстуре.
- Тесты анализатора ролей на размеченных примерах.
- API-тесты на основные сценарии.
- GitHub Actions: тесты бэкенда, линтер, сборка фронтенда на каждый push.
